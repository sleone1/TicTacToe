❯  it feels inefficient to iterate over the board to build a player list, then  
  the players to get a winner, but I like the readability and shared logic. Do  
  I have alternative options?                                                   

⏺ Yes, there are a few. First, though: at this size it doesn't matter. A 4×4
  board has 20 possible wins (4 rows, 4 columns, 2 diagonals, 4 corners, 9
  boxes) of 4 cells each, so the worst case is about 80 cell reads and 20 small
  arrays. The JVM probably optimises the short-lived arrays away entirely. The
  double pass costs almost nothing.

  If you want a single pass anyway, here are the options from least to most
  change:

  1. Pass a cell lookup instead of an array. getSetWinner takes a length and a
  function that fetches each cell. It reads cells one at a time and stops at the
  first mismatch, so no array is built:

  getSetWinner(size, k -> board.getCell(k, i));                 // column i
  getSetWinner(size, k -> board.getCell(k, k));                 // down diagonal
  getSetWinner(size, k -> board.getCell(k, size - 1 - k));      // up diagonal

  It's one pass with early exit and keeps the shared logic. The checks get
  shorter than the current loops, but the lambdas are a bit less obvious to
  read.

  2. Win conditions as data (my pick). Build a list of every winning line once,
  as cell coordinates, in a static field. checkWinner then becomes a single
  loop: for each line, read its cells off the board and stop at the first
  mismatch. All the "what counts as a win" logic sits in one place, the checking
  runs in one pass, and nothing is rebuilt per call. Adding a new kind of win
  means adding coordinates, not a new block of code. The one wrinkle is that the
  board size has to be known when the list is built, which works because SIZE
  is a constant.

  3. Bitboards. Store each player's cells as one 16-bit number, with one bit per
  cell, and keep each winning line as a precomputed bit pattern. Checking a
  line is then a single operation: (xBits & line) == line. It's by far the
  fastest, but it means rewriting Board, and the code becomes much harder to
  read. It's only worth it for something like an AI that checks millions of
  boards.

  4. Only check lines through the last move. After a move, only the lines
  through that cell can have become a win. This is the biggest saving in
  practice, but it changes the API: checkWinner would need the last move, not
  just the board.

  Option 2 fits what you said you value: it's readable, keeps the logic shared,
  and avoids the double pass. Want me to implement it?
